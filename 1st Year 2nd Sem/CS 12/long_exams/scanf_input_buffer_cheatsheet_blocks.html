Input buffer — mental model

The buffer is a conveyor belt of characters. When you type 42\n and press Enter, every character queues up left-to-right. scanf picks characters off the front; anything it doesn't want stays for the next call.

User types "42" + Enter → buffer contains:
'4'
'2'
'\n'
→ →
'\n' is always left behind by %d and %s
%d — reading an int
1
Skip all leading whitespace (spaces, tabs, \n)
2
If next char is + or -, eat it
3
While next char is a digit, eat it
4
Stop at first non-digit — leaves it in buffer
Buffer trace — scanf("%d", &n) on " 42\n"
' '
'4'
'2'
'\n'
blue = skipped ws green = eaten red = stays
'\n' left in buffer — next %c will grab it immediately!
%c — reading a char
1
Eat the very next character — no whitespace skipping!
Buffer trace — scanf("%c", &ch) after %d left '\n'
'\n'
'A'
'\n'

ch = '\n' — not 'A'! The leftover newline got eaten first.

Fix: add a space before %c to skip whitespace:
scanf(" %c", &ch); — the space eats any pending whitespace.
int n; char ch;
scanf("%d", &n);
scanf(" %c", &ch); // space before %c!
%s — reading a word
1
Skip leading whitespace (including \n) ✓
2
While next char is not whitespace, eat it
3
Stop at first whitespace — leaves it in buffer
Buffer trace — scanf("%s", buf) on "hello world\n"
'h'
'e'
'l'
'l'
'o'
' '
'w'
...
Cannot read strings with spaces. Use fgets for full lines.
No bounds checking — always risky with long input. Prefer fgets.
fgets — the safe alternative
1
Read chars from stream one by one
2
Stop when \n is eaten, OR n-1 chars read, OR stream ends
3
Always appends \0 — safe string guaranteed
4
\n is included in the output (unlike scanf)
char buf[8];
fgets(buf, 8, stdin);
// Input "hello\n" → buf = "hello\n\0"
// Input "toolongstring\n" → buf = "toolon\0"
// (reads max 7 chars + \0)

// Convert to int after fgets:
int n = atoi(buf); // needs stdlib.h
Predictable, size-safe, reads full lines including spaces.
Mixing fgets + scanf is tricky — fgets after scanf may grab leftover '\n' immediately (blank read).
The classic bug — %d then %c
int n; char ch;
scanf("%d", &n);  // user types "5\n"
// buffer now: ['\n']
scanf("%c", &ch); // eats '\n' ← bug!
printf("%c\n", ch); // prints newline, not input
ch = '\n' — user never got to type a character.
// Fix A: space before %c
scanf(" %c", &ch); // skips whitespace first

// Fix B: use fgets for the char line
char line[4];
fgets(line, 4, stdin);
ch = line[0];

scanf return value

Returns number of items successfully read. Check it to detect bad input:

if (scanf("%d", &n) != 1) {
    printf("bad input\n");
}
fgets + scanf mixing pitfall
// Scenario: scanf then fgets
int a; char line[100];
scanf("%d", &a);      // eats "5", leaves "\n"
fgets(line, 100, stdin); // eats "\n" → line="\n"!
// user never got to type the line
fgets after scanf reads the leftover '\n' as an empty line.
// Fix: consume leftover \n first
scanf("%d", &a);
int c; while((c=getchar()) != '\n' && c != EOF);
fgets(line, 100, stdin); // now safe
Best practice: pick one — use fgets for everything, or use scanf for everything. Mixing causes confusion.
